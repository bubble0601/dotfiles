# 機能の総括資料(Artifact)

## ユーザー入力

```
$ARGUMENTS
```

空でなければ最優先で考慮する。

## 何を作るか

実装を終えた機能を、チーム・CS・レビュアーが読んで分かり、そのまま動作確認にも使える 1 枚の HTML ページ。

- 読み手は、実装の中身を知らない人(CS、PO、他チーム)を想定する。だから技術的な詳細(migration の本数、API の検証、内部の挙動)は載せず、PR の本文に任せる。この資料は「何ができるようになり、何に気をつけ、どう確かめるか」に絞る
- 見た目と動きは `assets/template.html` が持っている。中身(各タブの HTML とテストケースのデータ)だけを毎回作り、`scripts/build.py` で組み立てる
- 完成形の例は `examples/legal-dayoff/`(変形休日の法定休日日数。実在の PR を匿名化したもの)。迷ったらここの `overview.html` `feature.html` `notes.html` を開いて、粒度と書き方を真似る

## 1. 材料を集める

会話・PR・計画書・テストケース md から集める。足りないものだけユーザーに聞く。

- PR: `gh pr view <番号>` の本文と、`git log --oneline <base>..HEAD`
- 仕様: 計画書(`docs/plans/` など)の課題・要望の原文、仕様の doc
- テストケース: E2E テストケース md(`docs/e2e/*.md`)のうち、この機能の行
- 事実の裏取り: 資料に書く仕様(表示名、初期値、条件、どの画面に結果が出るか)は、コードを読んで確かめる。会話や計画書に書いてあっても、コードと食い違っていることがある。確かめられなかったことは、本文で言い切らず、最後の報告でユーザーに伝える

## 2. 各タブの中身を書く

タブの構成は固定する(読み手が毎回同じ場所を見れば済むように)。各タブは見出しごとに白いパネル(`<section class="panel">` + `<h2>`)に分ける。

| タブ | パネル | 書くこと |
|---|---|---|
| 概要 | まとめ | 3〜4 行の箇条書き(`<div class="tldr"><ul class="plain">`)。何ができるようになったか、誰の困りごとが解決するか、既存の利用者に影響があるか |
| | 背景 | 課題。顧客の要望・ルールと、今まで何が困っていたか、どう対処していたか |
| 実装した機能 | 追加した設定 | 追加・変更した設定や画面。選択肢と初期値は表(`table.data`)にすると読みやすい |
| | Before / After | 変更前後の画面を並べる(`.grid2` の 2 つの `.box` に `.form-mock`)。追加した部分は `.fm-new` で点線で囲む |
| | (必要なら)具体例 | 数字で 1 つ示す表。例: 月ごとに必要な日数。ページ内で計算するなら `extra_script` に書く |
| 留意事項 | 前提条件 | この機能を使うのに要る設定・契約・条件 |
| | 顧客への案内事項 | CS が顧客に伝える・設定してもらうこと。既存データの扱い、表示名の変更、過去分への反映方法など |
| | 影響範囲 | 2 行程度。何が変わり、何が変わらないか |

文言の方針(ユーザーの指示から決めたもの):

- 見出しは短く抽象的にする(「留意事項」「前提条件」「顧客への案内事項」)。ただし誰が何をするかが消える言い方(「注意点」だけ)にはしない
- ブランチ名、base ブランチ、「◯◯時点」の日付は載せない。見出しの下は PR 番号のリンクだけでよい
- 画面の文言(ボタン名・表示名・エラー文)は、コードと一字一句同じにする
- 書き終えたら、yomiyasu スキルで地の文を推敲すると読みやすくなる(テストケースの文言は md の写しなので対象にしない)

## 3. テストケースを用意する

### 画面のケース

E2E テストケース md から、この機能の行を抜き出す。

```bash
python3 <このスキルのディレクトリ>/scripts/extract_cases.py docs/e2e/<画面>.md --match <ID の正規表現> --group <画面名> -o cases-screen.json
```

### 結果が別の画面に出るケース

設定画面で決めた値の結果が、別の画面(給与・請求など)に出る機能では、その画面で結果を確かめるケースがほしくなる。E2E のルールでは「期待結果が出る画面の md に置く」ので、設定画面の md には入っていないことが多い。

- 作るなら、先にユーザーに置き場所(資料だけか、その画面の md にも正式に足すか)と範囲(代表だけか、全組み合わせか)を聞く。全組み合わせは単体テストが押さえていることが多く、資料では代表に絞るのが既定
- 期待値は、結果が出る画面のコードと計算の処理を読んで決める。画面のどこに何が出るか(合計欄の名前、色、単位)を確かめ、値が画面に出ない条件(例: 勤務の無い日が法定休日になっても休日労働の時間は増えない)にも気をつける
- 前提のデータが重い(何十日分の実績など)ときは、そのことを備考と最後の報告に書く
- 形は `examples/legal-dayoff/cases-downstream.json` と同じ JSON にする(`group` に画面名、`purpose` は「〜ことを確認する」で終える。表示時に「を確認する」は外れる)

### 表の仕様(雛形が持っているもの。変えたいときだけ雛形を直す)

- 列は「目的 / 前提条件 / 手順 / 期待結果 / 判定 / コメント」。テストケース ID・ランク・自動テストの有無は出さない(読み手の CS には要らない)
- 判定は OK / NG の 2 つ。グループ(画面)ごとに見出し行が入る
- 表の上に、表示の絞り込み(すべて / 未判定だけ / NG だけ)と、右寄せのボタン(判定をすべて消す / NG とコメントがあるものだけコピー / 結果をコピー)
- コピーは Markdown のチェックリスト。ID は入れない
- 判定とコメントはそのブラウザにだけ保存される。説明文はそのことの 1 文だけにする

## 4. 組み立てて公開する

1. 作業用のフォルダ(scratchpad など)に `spec.json` と、`overview.html` `feature.html` `notes.html`、ケースの JSON を置く。`spec.json` の形は `examples/legal-dayoff/spec.json` を参照。`key` は保存に使う名前で、機能ごとに変える(同じにすると別の資料の判定が混ざる)
2. 組み立てる。ページ内のスクリプトの構文も確かめる

   ```bash
   python3 <このスキルのディレクトリ>/scripts/build.py <作業フォルダ>/spec.json <作業フォルダ>/summary.html
   ```

3. 公開する前に、ブラウザで開いて確かめる。`build.py` の構文チェックは UTF-8 で読むので、文字化けや CSS でタブが切り替わらない不具合には気づけない(実際にあった)

   ```bash
   python3 -m http.server <空いているポート> --bind 127.0.0.1 --directory <作業フォルダ>   # バックグラウンドで起動
   ```

   Playwright MCP で `http://127.0.0.1:<ポート>/summary.html` を開き、次を確かめる。終わったらサーバを止める(`file:` は Playwright MCP で開けない)
   - コンソールにエラーが無い
   - 4 つのタブを順に押して、押したタブの中身だけが見える(`#overview` `#feature` `#notes` `#cases` の表示)
   - テストケースの OK / NG を押すと行の色が変わる
   - 図や表を足したタブは、スクリーンショットで崩れていないかを見る

4. `summary.html` を Artifact として公開する。使えるツールで公開すればよい(ファイルから公開できるツールがあればそれを使う)。`icon` は初回だけ `checklist`。直したら同じ Artifact に公開し直して、URL を保つ
5. 報告では、ブラウザで確かめた範囲(幅・公開先で見たか)を書く。非公開の Artifact なので、共有はページの共有メニューから行うことも伝える

## 直すとき

- 中身の直しは断片(`*.html`、ケースの JSON)を直して組み立て直す。見た目や表の動きの直しは `assets/template.html` を直す
- 保存の形(判定の種類など)を変えても、古い保存データの読み替え(後方互換)は入れない。必要なら「判定をすべて消す」で消してもらう
