# security-audit

プロダクトのセキュリティを、範囲(タブ)と小分類の枠で一通り洗い、問題・指摘・対策を 1 枚の HTML にまとめる。

資料は次の 2 つのファイルでできている。

- **security-review.html**: 表示側。中身に依存しないので、テンプレートをそのまま使う
- **security-review.data.js**: 中身。調査のたびにここだけを書き足す

1 回で終わらせる作業ではない。観点を 1 つずつ進め、そのたびに資料へ反映して commit する。数日にまたがる前提で進める。

## 構成

| ファイル | 中身 |
|---|---|
| `assets/security-review.html` | 表示側のテンプレート |
| `assets/security-review.data.js` | データの骨組み(範囲・小分類・攻撃者の立ち位置の初期値と、問題の書き方の例) |
| `references/phases.md` | 観点ごとの調べ方とコマンド。各観点に入る前に、その節を読む |
| `scripts/validate.mjs` | データの整合の検査。`node <skill>/scripts/validate.mjs <data.js>` |

## 始め方

1. 置き場所(例: `docs/security/`)とブランチを利用者と決める
2. `assets/` の 2 ファイルをコピーし、`meta.title` と `meta.storeKey` をプロダクトに合わせる
3. 範囲と小分類を、プロダクトに合わせて足し引きする。利用者に見せて合意してから調査に入る。利用者が範囲から外したいもの(ISMS など)は外す
4. 攻撃者の立ち位置(zones)も、プロダクトの利用者の種類に合わせて直す。たとえば LINE のユーザー、現場の作業員、委託先などを足す
5. 既存の資料(過去のギャップ分析、顧客向けの概要シート、想定問答集)があれば読み、小分類の `refs` に手がかりとして書く

## 観点の進め方

観点を 1 つ選ぶ。選んだら `references/phases.md` の該当する節を読み、調べる。順番は利用者に提案して選んでもらう。被害が大きく、スキャンでは見落としやすいものから進めるのがよい。

観点ごとに、次のことを決まりとする。

- **指摘の接頭辞を 1 文字決め、`meta.sources` に足す**: 調査の種類、リビジョン、日付、補足を書く。画面には出さず、調査の記録として残す。O と I は数字の 0 と 1 に見えるので使わない
- **調査役と反証役を分ける**: 広い観点(個人情報の流れ、業務ロジック)では、調査役のエージェントを数体と、反証役を数体動かす。反証役には結論ではなくコードを渡す。エージェントを動かす前に、数と費用の見込みを利用者に伝えて選んでもらう
- **候補は一覧で見せる**: 載せるか載せないかは利用者が決める。載せないと決めたものは資料に書かない。仕様と判断したものは excluded に理由付きで書く
- **調べた範囲と調べていない範囲を書き分ける**: grep だけ、IaC を読んだだけ、のように確かめ方が浅いものは、notExamined か問題の本文にそう書く
- **途中で前提が誤りと分かったら、すぐ直す**: たとえば「SSO はないと思っていたが、実はあった」と分かった場合。直したことは利用者に報告する
- **件数を報告するときは、validate.mjs の出力から写す**: 手で数えない

## 資料の書き方

### 問題と指摘

- 問題の記号は「小分類の key + 連番」(authn-1、ci-2 など)にする。足すときは、その小分類の次の番号を取る。振り直すと、利用者がブラウザに残したメモがずれる。やむを得ず付け替えるときは、html の `KEY_RENAMES` に旧→新の対応表を足す
- 指摘は、どれか 1 つの問題にだけ置く。対策は `fixes`(単独で解消する)と `reduces`(軽くするが、単独では残る)で指摘に結び付ける。他の問題の指摘を指してもよい
- 直った指摘は消さない。`resolved` を付け、どの対策で直ったかを追えるようにする
- 問題がなかった小分類も消さない。`checkedAt` を付けて「問題なし」と表示し、points に調べた結果を書く

### 何を書かないか

- 攻撃の記述は「誰が、どういう条件で」までにとどめる。再現の手順やペイロードは書かない
- 顧客向けの説明文書と実態が食い違うことは、検査の問題にしない。必要以上に渡している、消していない、という実害を問題にする。文書の側は別に直す。社内向けの想定問答集は、元の回答を残して「⚠️ 実態とのずれ (日付)」を注記する。顧客に出す概要シートは書き換えてよい
- 個人名は、書く前に載せる形(人数かイニシャルか)を利用者に確かめる

### 文章

- 気取った言い回しや比喩を使わず、文字どおりに書く
- 対策の本文には、「何をするか」と「それで何が防げるか」を書く。ブラウザのヘッダーのように仕組みが分かりにくいものは、ヘッダーごとに意味と、どのリスクに効くかを書く

### 画面で付けるステータスとメモ

一覧の行ごとに、ステータス(未検討・対応済み・対応予定・対応しない)とメモを付けられる。データには書かず、見ている人のブラウザ(localStorage)にだけ残る。

- ステータスを選んでいない問題は、指摘がすべて `resolved` なら対応済み、それ以外は未検討になる
- 対応済みにした問題の指摘は、上部の集計で対応済みに数え、深刻度の絞り込み(HIGH・MEDIUM・LOW)でも出さない
- 対応しないにした行は薄く表示する
- チームで共有するときは「書き出す」で Markdown にして渡す

## 確かめ方

資料を変えたら、次の 2 つを行う。

1. **整合の検査**: `node <skill>/scripts/validate.mjs <data.js>` を実行する。指摘 ID の重複、存在しない指摘を指す対策、どの対策にも結び付いていない指摘、記号の形を検査する
2. **表示の確認**: ローカルで配信し(`python3 -m http.server`)、ブラウザで開いて表示が崩れないことを見る
   - 同じポートで開き直すと、古い data.js がキャッシュから読まれることがある。ポートを変えるか、`fetch(url, {cache: 'reload'})` してから再読み込みする
   - Playwright のスクリーンショットは、作業ディレクトリに `.playwright-mcp/` を作る。確認の後に消す

## commit と共有

- 観点ごとに commit する。顧客向けの文書と想定問答集を直したときは、資料とは別の commit にする
- 資料には、まだ塞がっていない攻撃の経路が入る。PR やリポジトリに入れる前に、読める人の範囲(リポジトリに書き込める人数など)と、HIGH の経路を先に塞ぐかどうかを利用者に確かめる
